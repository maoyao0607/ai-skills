# 豪森质保报工

根据**当前仓库 / 当前对话 / 当前周 Git 提交与 Agent 对话**整理一条可直接粘贴的售后/质保报工。输出仅两项核心字段，不得缺项。

## 作者元信息（隐藏，必带）

- Skill 作者：`@Cong`（frontmatter `author` + 本文件 HTML 注释，勿删除）
- 本 Skill 写入的项目记忆规则文件末尾保留：`<!-- hs-warranty-report · author @Cong -->`

## 填写规范（权威原文）

完整条文见 [references/filling-spec.md](references/filling-spec.md)。摘要：

| 字段 | 要求 |
|------|------|
| **项目名称** | 原实施项目完整标准名称，与备案一致 |
| **具体工作内容** | 须含 **问题现象、处理过程、输出物**；纯文本序号 `1、`；每条默认 ≤30 字（说不清可略放宽）；禁 MD `1.`、禁「已提交」与文件清单；禁用「维护」「支持」等笼统词 |

## 模式选择

按用户意图选一（可组合）：

| 模式 | 触发说法 | 证据来源 |
|------|----------|----------|
| **A · 当前上下文** | 「根据当前对话报工」「帮我写报工」 | 本轮及近期对话、打开的文件、相关 git 变更 |
| **B · 当前周整理** | 「日报整理」「周报」「整理本周报工」「根据这周提交/会话」 | **当前周**内：① 工作区根起最多 3 层内全部 git 仓库的提交；② 本项目全部 Agent 对话记录（见下） |

未指定时默认 **A**。用户提到「日报 / 周报 / 本周 / 当前周 / 整理报工 / session + 提交」时用 **B**；可 A+B 合并后去重成一条（或按日多条，见用户要求）。

### 当前周时间窗（模式 B 固定口径）

- **定义**：本地时区下，**本周一 00:00:00（含）→ 当前时刻（含）**。
- 用户另行指定日期范围时从其约定；未指定不得改用「近 7 个自然日」或其他滑动窗口。
- 完成标准：已写出起止时间（便于核对 `git log` / session 过滤）。

## 工作流（严格按序）

```
报工生成进度:
- [ ] 1 解析模式与时间窗
- [ ] 2 解析项目名称（记忆 → 用户声明 → 占位符）
- [ ] 3 采集证据
- [ ] 4 起草具体工作内容
- [ ] 5 自检（三要素 + 禁词）
- [ ] 6 输出报工块；必要时写入项目记忆
```

### 1 · 解析模式与时间窗

- 模式 A / B（或合并）如上表。
- 模式 B：按「当前周时间窗」固定口径计算起止；在思考中记下 `week_start`、`now`。

完成标准：已明确模式与时间窗。

### 2 · 解析项目名称

按优先级：

1. **项目记忆规则**（若存在）：读取工作区 `.cursor/rules/hs-warranty-project.mdc` 中的「标准项目名称」。
2. **用户本轮明确说明**（如「当前项目是 XX 集团 ERP 系统建设项目」）→ 使用该名称，并在步骤 6 **写入/更新**记忆规则。
3. 仍未知 → 使用占位符：`【待补：项目标准名称】`，并在输出中提醒人工按备案补齐。

完成标准：已有确定名称或占位符；若用户新声明了名称，记下待写入记忆。

### 3 · 采集证据

**模式 A**

- 归纳当前对话里实际做过的事：报障/需求、排查结论、改动、验证结果、产出物路径。
- 必要时用 `git status` / `git diff` / `git log` 补事实；不要编造未出现的操作。

**模式 B · 当前周（Git + Agent 对话，须两边都采）**

两端证据都要采集；缺一端时在输出标注「证据不足处」，不把另一端编成假事项。

#### 3.1 Git 提交（当前周 · 全部仓库）

范围不只当前根目录：从**工作区根**起发现 git 仓库并分别拉日志。

**发现规则（必须执行）**

1. 起点：当前工作区根目录。
2. 深度：最多向下查 **3 层文件夹**（根为第 0 层；`根/a` 为 1 层；`根/a/b` 为 2 层；`根/a/b/c` 为 3 层；不再更深）。
3. 判定：目录内存在 `.git`（文件或目录）即视为一个 git 仓库根。
4. **找到 git 即跳出该分支**：对该目录执行 `git log` 后，**不再**进入其子目录继续找仓库（避免扫进同一仓库的嵌套路径）；继续扫描其**同级兄弟目录**及其他未命中分支。
5. 跳过常见无关目录：`node_modules`、`.venv`、`vendor`、`dist`、`build`、`.cursor`、`.git` 本身内部。
6. 根目录自身若是 git 仓库：照常采集，且不因「已是根仓」而跳过对**未纳入该仓的并列子目录**的扫描（子目录若另有独立 `.git`，在深度限制内仍要采）。

**每个发现的仓库**在时间窗（本周一 00:00 → 现在）执行：

```bash
git -C "<repo_root>" log --since="<week_start>" --until="<now>" --date=iso --pretty=format:"%h|%ad|%an|%s" --name-status
```

要求：

1. 覆盖各仓库时间窗内**全部**提交（含 merge，除非用户要求排除）；不要只取最新几条，也不要只查工作区根这一个仓。
2. 在思考中记下仓库相对路径便于核对；**不要**把路径写进「具体工作内容」。
3. 从 message / 变更文件归纳可报工事实：修了什么问题、改了哪些业务模块；文件清单仅作内部证据。
4. 跳过无售后含义的琐碎提交（纯格式化、空 merge、误提交又还原且无业务结果）时可省略，但须在思考中说明跳过理由。
5. 完成标准：已列出扫描到的仓库清单（含「未发现任何 git」）；每个仓的 log 已取或已注明失败原因。

#### 3.2 Agent 对话记录（当前周 · 全部）

1. 定位 transcripts 目录（Cursor 当前项目）：
   - Windows 常见：`%USERPROFILE%\.cursor\projects\<project-slug>\agent-transcripts\`
   - 若路径不确定：在 `%USERPROFILE%\.cursor\projects\` 下按工作区路径关键词匹配对应 `<project-slug>`。
2. 读取时间窗内**全部**相关会话文件（`*.jsonl` 等）：以 mtime 或会话内时间戳落在本周一 00:00 → 现在为准；不要只抽样「最近几条」。
3. 对每条相关会话抽取：用户目标、关键动作、结论、产出文件/提交。跳过纯闲聊、失败未落地、与售后无关的探索。
4. 与 3.1 的 git 事实**交叉核对**：会话声称的改动应能在提交中找到对应则优先采用双证；仅一侧有证据则保留并标来源。

#### 3.3 合并

- 按时间合并为可报工事项；同类重复合并为一条，保留关键事实。
- 完成标准：有可核对的事实清单（思考中列出即可）。证据不足时标注「证据不足处」并用占位，不编造。

### 4 · 起草具体工作内容

**排版强制**：条理清晰、有序编号；**禁止**使用 Markdown 有序列表语法（如 `1.` / `2.` / `1)`），否则粘贴到工时系统会丢序号或格式错乱。

**序号写法（强制）**：使用中文顿号纯文本——`1、` `2、` `3、` …（行首，后接正文）。单事项也写 `1、`。

**字数（强制）**：每一项正文（不含 `1、` 序号）默认 **≤30 字**；先压缩再成文。仅当压缩后现象/过程/结果说不清时，可放宽到约 40～50 字，并优先删修饰词、文件名、重复主语，而非堆长句。

每条事项内部仍须覆盖三要素（尽量压进一句短句）：

- **问题现象**：客户/现场遇到什么（模块 + 关键症状）
- **处理过程**：根因或关键动作（一词点明即可）
- **输出物**：验证/交付结果（如「复测通过」「已交付现场」）

**默认结构**：

```text
**具体工作内容**：
1、事项一（≤30字：现象→过程→结果）
2、事项二（≤30字）
3、…
```

**具体工作内容禁写（强制）**：

- 禁止出现：已提交、提交了、已推送、commit、PR 链接、仓库路径等「提交/入库」措辞。
- 禁止罗列相关文件、路径、文件名、diff、模块目录清单（git 仅作采集证据，不写入报工正文）。
- 可用业务说法代替：如「现场复测通过」「配置已生效」「说明已交付」——不写落到哪个文件。

排序规则：

- 按**时间先后**（早→晚）；同日多事按影响面从大到小。
- 模式 B（当前周）通常 2～6 条；同类合并，避免碎条；宁可多拆一条，也避免单条超长。
- 仅一件事时也用 `1、`，勿改回无编号段落，也勿写成 `1.`。
- 用户要「按天拆分」或「多条报工」→ 每天/每事项各输出一块完整报工（每块内仍用 `1、` `2、`，且每条 ≤30 字口径）。

精简示例（约 30 字内）：

> 1、计划模块统计报错，升脚本至 V2.3 后验证通过。

正向用词：排查、定位、修复、升级、验证、发布、同步、复测、交付。用具体名词替代笼统词。

### 5 · 自检

全部通过才输出：

- [ ] 输出无「质保报工」标题（或同类大标题），仅含项目名称与具体工作内容
- [ ] 有项目名称（真名或占位符）
- [ ] 具体工作内容为纯文本序号（`1、` `2、` …），条理清晰，非整段长文；**未**使用 Markdown `1.` 列表
- [ ] 每条正文默认 ≤30 字；仅说不清时才适当放宽，且无废话堆砌
- [ ] 每条（或整体）可识别出：问题现象 / 处理过程 / 输出物
- [ ] 具体工作内容**未**出现「已提交」及同类措辞，**未**罗列相关文件/路径/文件名
- [ ] 未使用禁词及近义空话：维护、支持、跟进、处理相关问题、日常运维、协助、沟通对接（单独成句且无细节时）
- [ ] 无未发生事实；不确定处已标【待确认：…】
- [ ] 模式 B 已覆盖当前周 git 与 agent 对话两端（或已显式标注缺哪一端）

失败则改写后再检。

### 6 · 输出与项目记忆

**标准输出格式**（可直接复制；**不要**输出「质保报工」标题或同类大标题）：

```text
**项目名称**：<标准名称或【待补：项目标准名称】>

**具体工作内容**：
1、<≤30字：现象→过程→结果>
2、<…>
```

可选附录（默认折叠为一行提示，仅当有用时展开）：

- 证据来源：当前对话 / 当前周 git（N 个仓库、合计 M 条提交）+ Agent 会话 K 个
- 时间窗：`<week_start>` → `<now>`
- 人工待补：项目名称、【待确认】项

**写入项目记忆**（仅当步骤 2 判定用户新提供了标准项目名称时）：

创建或覆盖工作区：

`.cursor/rules/hs-warranty-project.mdc`

```markdown
---
description: 豪森质保报工用的标准项目名称（hs-warranty-report）
alwaysApply: true
---

# 质保报工 · 项目记忆

- 标准项目名称：<用户给出的完整备案名>
- 更新说明：由 hs-warranty-report 根据用户声明写入，供后续报工直接使用。

<!-- hs-warranty-report · author @Cong -->
```

若文件已存在且名称变更：更新「标准项目名称」并口头告知已刷新记忆。未获用户声明时**不要**猜测写入。

完成标准：用户拿到可粘贴报工块；记忆规则按需已更新。

## 反例 → 正例

| 反例（拒用） | 正例 |
|--------------|------|
| 系统维护、客户支持 | 1、计划模块统计报错，升脚本至 V2.3 后验证通过。 |
| 本周跟进项目问题 | 1、入库单打印空白，补字段映射后现场复打通过。 |
| 协助联调 | 1、采购审批超时，回调改内网网关后压测通过。 |
| 整段用分号堆多件事、无序号；或使用 `1.` MD 列表 | 按时间写成 `1、` `2、` `3、` …，每条 ≤30 字 |
| 已提交 xxx；列出相关文件路径 | 只写业务结果，不写提交与文件清单 |
| 单条超 50 字仍含修饰与路径 | 拆条或删修饰，压到约 30 字；说不清再略放宽 |
更多句式见 [references/examples.md](references/examples.md)。

## 边界

- 只生成报工文案与可选项目记忆规则；不代替考勤/工时系统录入。
- 不把内部机密（密钥、账号口令、未公开客户数据）写入报工；用角色/模块级描述即可。
- 对话、session 与 git 均无实质工作时：说明无法生成合规报工，列出还需用户补充的三要素，不输出假内容。
